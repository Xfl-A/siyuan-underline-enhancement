# 真实实例手工验证清单

本清单来自设计规格 §10.2，用于在**真实思源实例**上逐项验收。自动化单测覆盖不了的部分（渲染、导出、
发布、只读、移动端、跨设备同步、层叠顺序）只能在这里确认。英文版清单见文末的
[English checklist](#english-checklist)。

**第 3 项是关键证据**：只有它能证明装饰真的以 inline style 原样落进了 `.sy` 文件，而不是只停留在编辑器
内存里。**第 9、10、11、13、16 项的行为无法通过静态检查确认**，必须在这台实例上实测（见各项下的说明）。

## 3. `.sy` 文件里 `style` 属性原样落盘（保真性关键项）

| 项       | 内容                                                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 步骤     | 见下方「怎么查」；对第 2 项装饰过的块逐项核对                                                                                              |
| 预期结果 | 块 JSON 的 `content` 字段里 `style` 属性**原样**出现，含 `text-decoration-line`、`text-decoration-style`、`text-decoration-color` 三条声明 |
| 实际结果 | （待填）                                                                                                                                   |
| 结论     | ☐ 通过　☐ 不通过                                                                                                                           |

**怎么查**

1. 装饰保存后，块已经通过 `/api/block/updateBlock`（`dataType: "dom"`）落盘，`.sy` 文件里就是最终形态。
   直接从磁盘读，不要只看向编辑器 DOM。
2. 文件路径形如：

   ```text
   {workspace}/data/{notebookID}/{docID}.sy
   ```

   `{notebookID}` 与 `{docID}` 是思源生成的目录名（如 `20200812220555-lj3enxa`），不是文档标题。
   在思源里打开测试文档，URL 上的 `?id=` 参数即 `{docID}`；笔记本 id 可在
   `{workspace}/data/.siyuan/conf.json` 里按目录名对应关系查到。
3. 用文本编辑器打开该 `.sy` 文件。它**不是 HTML**，而是一个 JSON 对象 —— 思源存的是自己的 AST，不是块的内容 HTML。
4. 找到刚才装饰过的那段文字所在的节点。装饰会变成一个 `NodeTextMark` 节点，形如：

   ```json
   {
     "Type": "NodeTextMark",
     "Properties": {
       "style": "text-decoration-line: underline; text-decoration-style: wavy; text-decoration-color: #0090ff"
     },
     "TextMarkType": "text",
     "TextMarkTextContent": "被选中的文字"
   }
   ```

   插件只产出下划线，因此始终只有一个 `NodeTextMark`，`text-decoration-line` 为 `underline`。
5. 逐项核对：
   * `Properties.style` 里的 `text-decoration-*` 声明与面板上的设置**逐字一致**（包括颜色值与 `var(--b3-...)` 主题变量）。
   * 「跟随文字颜色」时 `text-decoration-color` 的值是字面量 `currentColor` —— 整条声明必须存在。
     省略它虽然渲染等价，但思源会因此把颜色补成一条 `color:` 声明（那是文字色，不是装饰色），装饰颜色就失效了。
   * 装饰**只由 style 承载**：识别与清除完全依赖 `text-decoration-line`，不依赖任何自定义标记属性。
     这不是风格偏好 —— 思源解析块 HTML 时会丢掉自定义属性，只把 style 原样存进 AST，
     靠自定义属性识别装饰的插件在落盘后就再也认不出自己的装饰。
   * 文字本身没有被改写，也没有多出空壳块或重复块。
   * 关掉思源、重新启动后再次查看该 `.sy`，内容应完全不变。

## 13. 撤销：内核重渲染把块 HTML 规范化之后（桌面端，本项刻意不刷新文档）

| 项       | 内容                                                                                                                                                               |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 步骤     | 桌面端装饰一段文字 → **保持面板开着、不刷新文档** → 在不输入任何字符的前提下让思源重渲染这个块（把光标点进这一段并用方向键来回移动、折叠再展开该块等）→ 点「撤销」 |
| 预期结果 | 装饰被移除，文字一字未变。若按钮**仍是可点状态、点了却什么也不发生**，即为不通过（见下方说明）                                                                     |
| 实际结果 | （待填）                                                                                                                                                           |
| 结论     | ☐ 通过　☐ 不通过　说明：按钮可点但点了没反应（见下方说明）                                                                                                         |

> **这一项无法用自动化测试覆盖，也是撤销最大的单点风险。** 撤销的过期校验是逐字节比对
> `块 DOM 的 outerHTML` 与记录里的 afterHTML（`src/persist.ts` 的 `resolveUndoTargets`）。只要内核、
> 思源或任何一次后续渲染把这段 HTML 规范化了一点点（属性顺序、大小写、空格、实体写法），
> 每一条记录都会被判成过期并**静默丢弃**：栈顶被弹出、文档不变、面板也不重画，
> 于是按钮仍然是可点的，点下去什么也不发生。
> 因此本项必须实测；若不通过，请连同「重渲染前后块 DOM 的 outerHTML 差异」一起记录，那才是要改的地方。
>
> **本项刻意不刷新文档**：撤销栈只活在当前这次面板会话里 —— `src/index.ts` 在面板关闭时就 `clearChanges()`，
> 而刷新页面会连 JS 上下文一起销毁，栈必然是空的，那种情形下「撤销」应当是**禁用**状态，
> 测不出上面说的风险（本项之前写成「重载之后再撤销」，按字面执行必然失败：预期结果永远不成立）。
> 顺带确认：若重载文档或重开面板之后「撤销」仍可点，说明栈没被清掉，属于缺陷。
